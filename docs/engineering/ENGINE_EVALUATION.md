This is an engine-selection comparison, not evidence that an unintegrated engine is installed or tested. **Status correction:** this document's original opening inventory was overtaken by later work. ## OCR candidates

| Candidate | Evidence and trade-offs | Decision / gate |
| --- | --- | --- |
| [Google ML Kit text recognition](https://developers.google.com/ml-kit/vision/text-recognition/v2/android) | On-device recognition; the bundled model is available at install time but adds roughly 4 MB per script per architecture, per vendor documentation. The Play Services variant downloads models dynamically. Its [terms/privacy](https://developers.google.com/ml-kit/terms) state input and output remain on device, **but** APIs may contact Google and send performance/utilization metrics. The community Flutter plugin is a bridge, not the recognizer itself. | **Not integrated.** Current product constraint is no analytics or silent downloads. A bundled model alone does not establish that ML Kit meets that constraint. Do not substitute an unreviewed opt-out claim; any future use requires an explicit policy decision and verified behavior. |
| [Tesseract](https://github.com/tesseract-ocr/tesseract) + [Tesseract4Android](https://github.com/adaptech-cz/Tesseract4Android) | Local OCR; Apache-2.0 engine/wrapper, with separate Leptonica, libjpeg and libpng notices. [`tessdata_fast`](https://github.com/tesseract-ocr/tessdata_fast) has an Apache-2.0 repository licence; its LSTM data requires the correct engine mode. Languages need explicitly bundled or user-approved model files. Tesseract4Android describes native/JNI integration and notes its API is not thread-safe. | **Subsequently integrated in source:** Tesseract4Android and bundled language models are present. Native/device operation, binary provenance, memory and recognition quality still require verification; see [current status](CURRENT_STATUS.md). |
| [`flutter_tesseract_ocr` 0.4.31](https://pub.dev/packages/flutter_tesseract_ocr) | The inspected package includes a prebuilt Android AAR and copies configured trained data into app-private documents. Its Android wrapper initializes a shared `TessBaseAPI`, uses `AsyncTask`, and does not check the return from `init`; the bundled AAR's exact provenance/licence inventory and compatibility with this project's AGP 9 build were not established in this review. | Not adopted as-is: native execution, recovery, threading, binary provenance and third-party notices need investigation. Do not equate a Dart mock with a device OCR test. |

A future OCR slice must demonstrate real text from known bundled samples, editable review, language/model disclosure, failures, privacy, resource bounds and source preservation. A searchable PDF additionally needs an accurately positioned text layer and independent search/extraction checks; an image PDF plus a separate TXT file is not searchable.

## PDF reading and manipulation

The Dart `pdf` package creates documents; the separate `dart_pdf_editor`/`pdf_document` integration now supplies an existing-PDF route in source, with validation still pending. At the time of this original comparison, Android's [`PdfRenderer`](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer) can render pages starting with API 21; it requires a seekable descriptor and careful page/renderer lifecycle and memory management. Newer API-specific text, annotation and password features must not be assumed on older Android versions. It is a candidate for an Android-first read-only slice, but has not been implemented or tested here.

[PDFium](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/LICENSE) is another candidate for rendering and selected document operations; the project licence includes BSD- and Apache-style material and its distribution includes additional third-party components. A maintained wrapper, pinned binaries, per-ABI size, security updates, malformed/encrypted files, content-URI handling and actual capabilities must be audited before adoption. Neither Android rendering nor PDFium alone proves safe merge, editing, annotations, searchable PDF creation or compression. PDFium itself has not been added; the separate Dart editor is described in [PDF support](PDF_SUPPORT.md).

## Office formats and LibreOffice

[LibreOffice](https://www.libreoffice.org/licenses/) is principally MPL-2.0 with many additional component licences; distribution requires an exact-build notice and source-availability review. It is a desktop-oriented, substantial native engine, **not** a drop-in Flutter/Android package. An embedded Android port would need a maintained build, ABI coverage, sandboxing, size/startup/memory measurements, lifecycle and native integration. An optional desktop executable can be evaluated on supported desktop systems; a remote service can offer broader conversions but introduces explicit network consent, privacy, operating cost, credentials and service maintenance. Neither is implemented or configured.

For each future DOCX/XLSX/PPTX or ODF route, test real documents including fonts, tables, embedded media, macros and formulas; preserve originals; report unsupported/lossy features and validate the output in an independent application. A file-extension rename is never a conversion. No commercial, copyleft or other compatibility conclusion is implied by this research.

## Next bounded vertical slice

After the current source is built and exercised on actual Android hardware, prioritize a pinned, no-telemetry Tesseract integration with one clearly disclosed local language model and a real image → reviewed TXT workflow. Gate on native build, offline recognition, quality measurements, lifecycle/storage-failure tests and full native dependency notices. Add a searchable PDF only after recognized word geometry and independent PDF text-layer verification work. In parallel, assess a limited Android PDF reader; avoid promising office conversion until a maintainable engine and tests exist.
